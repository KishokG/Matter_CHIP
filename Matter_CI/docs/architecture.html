The Matter CI Pipeline

An automated, nightly pipeline that compiles the Matter SDK on a Mac mini, ships the binaries through Google Drive, and runs the certification test suite on a Raspberry Pi — then emails a full pass/fail report. Eight GitHub Actions jobs across two self-hosted machines, driven entirely from configuration.

Zoom In

How a test actually runs on the Raspberry Pi

The Pi is the interesting part: it behaves like a real Matter controller talking to a real device over the network. This is what run_tests.py does for every test case.

  1. Stage the exact build

    prepare_rpi_tests.py pulls the newest bundle from Drive, checks the Pi's SDK out to the same commit that was built, and symlinks the prebuilt binaries into place — so the test scripts and the binaries always match.

  2. Launch the device (DUT)

    The device-under-test app (e.g. chip-all-clusters-app) is started in the background with subprocess.Popen in its own process group, and its log is captured live on a background thread.

  3. Wait until it's ready

    The harness watches the device log for its startup / pairing signal before starting the test — instead of a blind fixed delay — mirroring how the upstream Matter CI runs.

  4. Drive the certification test

    The SDK's own Python test (e.g. TC_ACE_1_6.py) runs in the built controller virtualenv, commissions the device on-network, and exercises the cluster under test.

  5. Handle real device behaviour

    Auto-answers operator prompts on stdin, injects events through a named pipe, orchestrates factory-resets / reboots, and forwards commands to Fabric-Sync bridges — all the things a human tester would otherwise do by hand.

  6. Score & report

    The test's result summary is parsed into PASS / PASS* / FAIL / ERROR / RERUN / CANCEL, and the whole run is rendered to a filterable report.html.

Key Idea

Build once, test against the very same code

The pipeline never vendors the Matter SDK — it consumes the upstream project in two coordinated places, pinned to one commit so results are always trustworthy.

Build side · Mac mini

Compile the SDK

  • Clone + fetch connectedhomeip to the latest commit
  • Build ~19 device apps + chip-tool
  • Build the Python controller wheels
  • Stamp the exact commit into the bundle
bundle
via Drive
Test side · Raspberry Pi

Test the SDK

  • Check the Pi's SDK out to that same commit
  • Drop in the prebuilt binaries + wheels
  • Run the upstream certification test scripts
  • Report PASS / FAIL per test case

Why it matters: the binaries running on the Pi and the test scripts driving them come from one identical commit of the Matter SDK. There is never a mismatch between "what we built" and "what we tested" — the foundation of a trustworthy certification result.
